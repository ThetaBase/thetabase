The safety gate belongs inside the database, not in front of it.

ThetaBase is a branchable database for teams whose agents write to production. A rule-based classifier decides which schema changes need a human — and it runs inside the engine, where a connection string cannot route around it.

In April 2026, an agent deleted a production database and its backups

A Cursor agent running Claude Opus 4.6 destroyed PocketOS's database through a single Railway API call. Railway wrote it up and shipped guardrails in response.

You already know agents can do this. The question is what stops it — and most answers stop it in a proxy, which is a thing an agent with your connection string steps around.

A control plane can be bypassed by opening a connection. A gate inside the engine cannot.

Ninety seconds to watch it work

curl -fsSL https://thetabase.dev/install.sh | sh

theta login github
theta use acme checkout --create     # provisions in one round trip
theta demo                           # seeds a table to work against
theta schema propose drop-legacy-ref.json

That last command proposes dropping a column five rows depend on. Instead of dropping it:

chg_8f2a
  drop column on customers.legacy_ref — 5 row(s), irreversible
  A destructive change on a protected branch needs a human.

Validated on shadow branch 2. Review it, then:
  theta schema show chg_8f2a
  theta schema promote chg_8f2a
  theta schema reject chg_8f2a --reason "..."

The change was applied to a shadow branch and validated there, so what comes back already says what the checks found. Nothing touched main.

A change you confirm still happens. theta schema promote drops the column. The gate exists to make sure a person decided — not to decide for them.

The rules decide what a human ever has to look at

The other approach is "branch everything, a human reads the diff." That does not survive the first busy week: a person reading every diff is a person who starts approving without reading, and then the review is decorative.

ThetaBase classifies first. Only the destructive minority reaches anybody.

  • Rule-based, never model-inferred. Classification is a pure function of the change kind, the rows it touches, whether it is reversible, and whether the branch is protected. There is no prompt to inject, because there is no model in the decision.
  • Three tiers, not a yes/no. Safe changes apply. Destructive ones need a confirmation. The irreversible, high-impact ones cannot be cleared by confirmation at all — they are validated on a shadow branch and promoted.
  • A blast-radius breaker for the case where every individual write is fine and the sequence is not.

Branch creation is 3.7× faster than Dolt and 19× faster than PostgreSQL, and does not scale with the size of the parent. That is the claim, and it is the only one this table supports.

The rows in red are ours to lose: PostgreSQL reads faster at the root and writes three times faster than we do. They are here because you would find them yourself, and because a database that overstates its guarantees is the last thing you want gating your production schema.

What you get, and what you do not

  • Branches are free — on every plan, including the free one. Structural sharing means a branch copies no data, so it costs us almost nothing and we are not going to pretend otherwise.
  • Your data leaves whenever you want. theta eject exports to a standard form and runs without our involvement. Your ability to leave should not depend on our cooperation.
  • An append-only log is the only source of truth. Every state is a fold over it, so "what happened and who did it" is answerable.
  • An MCP server, so your agent talks to the database through the same gates you do — and cannot confirm its own proposals.
  • No SLA yet. We have not run a production quarter, so we are not publishing an availability number. When we have measured one, it will be here.
